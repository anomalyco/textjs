<!-- s:88013af27d -->
middleware پیش از تکمیل درخواست، کد را اجرا می‌کند. می‌تواند تغییر مسیر دهد، مسیر را بازنویسی کند، هدرها و کوکی‌ها را تنظیم کند یا خودش پاسخی برگرداند.

<!-- s:895d99d1b5 -->
قرارداد

<!-- s:9e6d75b727 -->
فایل `middleware.ts` را در ریشه پروژه (یا `src/`)، کنار `app/` ایجاد کنید. یک تابع `middleware` (یا یک خروجی پیش‌فرض) و یک `config` اختیاری صادر کنید.

<!-- s:a4d39cdaaf -->
middleware پیش از [کنترل‌گرهای مسیر](/docs/route-handlers)، فایل‌های ایستا و صفحه‌های کنسول، در `text dev`، `text start` و هر [آداپتور استقرار](/docs/deploying) سرور اجرا می‌شود. از `Request` و `Response` وب استفاده می‌کند، بنابراین همان فایل روی Node، Bun، Vercel Edge و Cloudflare Workers اجرا می‌شود.

<!-- s:dda0880da2 -->
تطبیق مسیرها

<!-- s:1e1ec8c339 -->
بدون `config.matcher`، middleware برای هر درخواست اجرا می‌شود. تطبیق‌دهنده‌ها از همان نحو Next.js استفاده می‌کنند:

<!-- s:473d472bc8 -->
| تطبیق‌دهنده | موارد منطبق |
| :-- | :-- |
| `/about` | `/about` و `/about/` |
| `/blog/:slug` | `/blog/hello` |
| `/docs/:path*` | `/docs`، `/docs/a/b` |
| `/a/:rest+` | `/a/b`، به‌جز `/a` |
| `/user/:id(\\d+)` | `/user/42`، به‌جز `/user/ada` |
| `/((?!api/).*)` | همه‌چیز به‌جز `/api/*` |

<!-- s:256aeeefbc -->
با `has` و `missing` شرط اضافه کنید (هدر، کوکی، پرس‌وجو یا میزبان):

<!-- s:d756420343 -->
تطبیق‌دهنده‌ها روی نام مسیر بدون `basePath` اعمال می‌شوند. در `text dev`، درخواست‌های ماژول خود Vite ‏(`/@vite/*`، فایل‌های منبع) هرگز middleware را اجرا نمی‌کنند.

<!-- s:75cd7297e6 -->
هر میزبان پیش از اجرای middleware، یک نام مسیر معیار تعیین می‌کند و از آن برای تطبیق، `request.nextUrl` و جست‌وجوی مسیر، کنترل‌گر و فایل استفاده می‌کند. کدگذاری‌های درصدی رمزگشایی می‌شوند و مسیر به شیوه‌ای که `new URL()` آن را می‌نویسد دوباره کدگذاری می‌شود، بخش‌های `.` و `..` حل می‌شوند و اسلش‌های تکراری و انتهایی حذف می‌شوند. مسیر `/ad%6din//users/` به‌شکل `/admin/users` به middleware می‌رسد، درحالی‌که `/café` به‌شکل `/caf%C3%A9` باقی می‌ماند. تطبیق‌دهنده‌ای که با اسلش انتهایی نوشته شده باشد، مانند `/admin/`، با `/admin` منطبق می‌شود. درخواست‌هایی که مسیرشان اسلش یا بک‌اسلش کدگذاری‌شده (`%2F`، `%5C`)، نویسه کنترلی یا کدگذاری درصدی نامعتبر داشته باشد، پاسخ `400` می‌گیرند. مسیرها به بزرگی و کوچکی حروف حساس‌اند: `/Admin` با `/admin` منطبق نمی‌شود و فایل‌های ایستا فقط با نام دقیق خود ارائه می‌شوند.

<!-- s:3f5746eb4e -->
نشانی‌هایی را که فایل در آن‌ها ارائه می‌شود تطبیق دهید، نه فقط نام فایل را. Cloudflare Pages فایل `report.html` را در `/report` هم ارائه می‌کند، بنابراین تطبیق‌دهنده‌ای برای `/report.html` از `/report` محافظت نمی‌کند. هر دو را در فهرست بیاورید، `matcher: ["/report", "/report.html"]`، یا فایل‌های محافظت‌شده را در یک دایرکتوری نگه دارید و آن را تطبیق دهید، مانند `/reports/:path*` برای فایل‌های داخل `public/reports/`.

NextResponse

<!-- s:880215c229 -->
| API | اثر |
| :-- | :-- |
| `NextResponse.next()` | ادامه به مسیر |
| `NextResponse.redirect(url, status?)` | `307` به‌صورت پیش‌فرض؛ `url` باید مطلق باشد |
| `NextResponse.rewrite(url)` | ارائه مسیری دیگر؛ مبدأهای خارجی پروکسی می‌شوند |
| `NextResponse.json(body, init?)` | پاسخ با JSON |
| `new Response(...)` | پاسخ با هر محتوایی |

<!-- s:a8292924c3 -->
برای ادامه بدون تغییر، چیزی برنگردانید. توابع `next()` و `rewrite()` برای تغییر وضعیت پاسخ نهایی، `{ status }` را می‌پذیرند. فقط پاسخ‌های ساخته‌شده با `NextResponse.next()` / `NextResponse.rewrite()` مسیریابی را هدایت می‌کنند: هر `Response` دیگری، از جمله پاسخی که `fetch()` برمی‌گرداند، پس از حذف هدرهای `x-middleware-*`، بدون تغییر به کلاینت فرستاده می‌شود.

<!-- s:583e778785 -->
در `request.nextUrl`، مقدار `basePath` از `pathname` حذف می‌شود، اما `href` و `toString()` آن را شامل می‌شوند. برای ماندن در محدوده برنامه، از آن یک کپی بسازید: `const url = request.nextUrl.clone(); url.pathname = "/login"; return NextResponse.redirect(url);`.

هدرها

<!-- s:37748fa2c3 -->
برای تغییر آنچه کنترل‌گرهای پایین‌دست دریافت می‌کنند، `request.headers` و برای افزودن هدرهای پاسخ، `headers` را ارسال کنید:

<!-- s:60bf4677c2 -->
هدرهای پاسخ middleware به پاسخ نهایی اضافه می‌شوند، مگر اینکه کنترل‌گر مسیر همان هدر را تنظیم کند.

<!-- s:ef657b8fe3 -->
کوکی‌ها

<!-- s:5d3635224b -->
ویژگی `request.cookies` هدر `Cookie` را می‌خواند؛ ویژگی `response.cookies` هدر `Set-Cookie` را می‌نویسد.

<!-- s:4a7b6bbf62 -->
کوکی‌های تنظیم‌شده در پاسخ `next()` یا `rewrite()` برای کنترل‌گر مسیر در همان درخواست نیز قابل مشاهده‌اند.

نکات

<!-- s:971c06c875 -->
- صفحه‌های رندرشده در کلاینت در مرورگر رندر می‌شوند، بنابراین بازنویسی به صفحه‌ای دیگر، فایل ارائه‌شده را تغییر می‌دهد، نه مسیری را که برنامه کنسول رندر می‌کند. بازنویسی به کنترل‌گرهای مسیر، فایل‌های ایستا و مبدأهای خارجی مطابق انتظار عمل می‌کند.
- middleware می‌تواند بدنه درخواست را بخواند؛ کنترل‌گرهای مسیر همچنان آن را دریافت می‌کنند. بدنه درخواست‌هایی که تطبیق‌دهنده کنار می‌گذارد هرگز دست‌کاری نمی‌شود.
- ویژگی `request.url` همیشه مبدأ سرور را دارد: هدف‌های درخواست مانند `//other.host/x` به یک اسلش آغازین نرمال‌سازی می‌شوند.
- [آداپتور ایستا](/docs/deploying#static) نمی‌تواند middleware را اجرا کند.
